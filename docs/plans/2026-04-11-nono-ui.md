# Nono UI Integration Proposal

## Goal

Make `nono.sh` feel like a first-class Roux capability instead of a hidden launch-time option on the built-in Claude profile.

This is a UI/product proposal, not an implementation plan. It is scoped to what Roux already knows how to do today, plus the smallest backend additions needed to make the UI honest.

## Verified Current State

- Roux currently detects whether `nono` is installed and lists profile names from `~/.config/nono/profiles/`.
- The only visible `nono` UI is the `Sandbox Profile (nono.sh)` select in [`src/lib/components/NewSessionDialog.svelte`](/Users/sphinizy/src/github.com/phin-tech/roux/src/lib/components/NewSessionDialog.svelte).
- That select only appears for the built-in Claude profile on the legacy launch path (`useLegacyClaudePath`).
- The backend applies `nono` by wrapping Claude with `nono run --profile <profile> --allow-cwd -- claude ...` in [`src-tauri/src/pty.rs`](/Users/sphinizy/src/github.com/phin-tech/roux/src-tauri/src/pty.rs).
- Non-Claude profiles and layout-created Claude panes do not currently go through the same wrapping path.
- Roux does not persist sandbox metadata on the `Session` record, so after launch there is no session-level UI that can reliably say whether a pane is sandboxed or which profile it used.

## Product Reality

`nono` exposes more than “pick a profile”:

- Named security profiles with workdir access, filesystem rules, network policy, secrets, and optional hooks.
- `nono why` for explaining whether a path or host is allowed or denied.
- `nono shell` for interactive sandboxed shells.
- Built-in Claude profile behavior, including TTY-preserving interactive mode and hook installation.

That means the right UI is not a bigger dropdown. Roux needs three surfaces:

1. setup and defaults
2. launch-time intent
3. in-session visibility and debugging

## Main UX Problem

Today the UI asks a launch-only question and then hides the answer forever.

That creates four problems:

- Users cannot tell which sessions are sandboxed.
- Users cannot inspect what a profile means without leaving Roux.
- Users cannot debug denials from inside Roux.
- The current UI implies general support, but the behavior is actually limited to one creation path.

## Recommended Information Architecture

### 1. Setup Surface

Add a small `nono` card either in onboarding or Settings.

Suggested contents:

- Install status: `Installed` / `Not found`
- Profile count: `3 profiles found`
- Primary CTA when missing: `Install nono`
- Secondary CTA when installed: `Open profile folder`
- Tertiary CTA: `Refresh`

Reasoning:

- This keeps `NewSessionDialog` focused on launching work, not explaining tooling prerequisites.
- It creates one obvious place to recover from “why don’t I see sandbox options?”

Suggested location:

- A new `Security` section in [`src/lib/components/SettingsPanel.svelte`](/Users/sphinizy/src/github.com/phin-tech/roux/src/lib/components/SettingsPanel.svelte)
- Optional first-run callout in [`src/lib/components/SetupPrompt.svelte`](/Users/sphinizy/src/github.com/phin-tech/roux/src/lib/components/SetupPrompt.svelte) only if Claude is installed and `nono` is missing

### 2. Launch Surface

Replace the current conditional dropdown with a small grouped “Security” section in `NewSessionDialog`.

Suggested shape:

- Section label: `Security`
- Primary toggle:
  - `No sandbox`
  - `Use nono profile`
- When `Use nono profile` is selected:
  - profile select
  - small capabilities summary
  - warning if the selected launch path cannot honor `nono`

The summary line matters. Example:

- `Profile claude-code: read/write project, access ~/.claude, network on`
- `Profile offline-review: read-only project, network blocked`

That keeps the decision legible without making users inspect raw TOML.

#### Important honesty rule

If the user picks a spawn path that Roux cannot actually sandbox, the UI should not quietly hide the control. It should show the section in a disabled or limited state with a direct explanation:

- `nono sandboxing is currently available only for built-in Claude launches.`
- `Custom profiles and layout panes will ignore this setting for now.`

That is better than the current disappearing control because it teaches the model boundary instead of obscuring it.

### 3. Session-Level Visibility

Every sandboxed session should advertise that fact after creation.

Suggested minimal treatment:

- Add a muted badge in the session card or tab:
  - `nono`
  - optional profile suffix: `nono: claude-code`
- Add a fuller line in a details popover or status area:
  - `Sandboxed with nono profile claude-code`

This requires session metadata. Recommended fields:

- `sandbox_provider: "nono" | null`
- `sandbox_profile: string | null`
- `sandbox_mode: "profile" | "custom" | null`

Even if only profile mode exists in v1, adding explicit metadata avoids painting the app into a corner later.

### 4. Session Inspector / Details Popover

Give sandboxed sessions a lightweight “what does this mean?” surface.

Suggested content:

- profile name
- working directory access level
- network policy: `allowed` or `blocked`
- secrets count or labels if available
- hooks installed: yes/no if available
- launch command preview

This should be read-only in the first pass. Editing policy from inside Roux is a larger product commitment and should come later.

### 5. Sandbox Debugging Surface

The highest-leverage deeper integration is `nono why`.

Suggested actions:

- `Why is this blocked?`
- `Check path access`
- `Check host access`

UI concept:

- A tiny command-palette action or session context-menu item opens a dialog.
- User chooses:
  - path + read/write/readwrite
  - or host + port
- Roux runs `nono why --json ...` with the active session’s profile context.
- Result renders in a structured explanation block:
  - `Allowed by profile filesystem.allow`
  - `Denied as sensitive path`
  - `Denied because network is blocked`

This is the place where Roux adds real value over “shell out to nono manually”.

## Concrete UI Proposal

If we want one coherent near-term design, this is the best sequence.

### Phase A: Make existing support visible and honest

- Add `Security` section to `NewSessionDialog`
- Stop hiding sandbox UI entirely on unsupported paths
- Add install/status row in Settings
- Persist `nono` session metadata and show a session badge

This is the minimum version that feels intentional.

### Phase B: Add read-only sandbox details

- Session inspector panel or popover
- Profile summary lines
- Copyable launch command

This turns `nono` from “mystery wrapper” into visible session state.

### Phase C: Add diagnostics

- `nono why` dialog
- Session context action: `Inspect sandbox access`
- Structured results, not raw CLI text

This is the first deeper integration that materially changes how users debug agent behavior.

### Phase D: Expand actual support surface

Only after the UI above is in place:

- support `nono` on non-Claude spawn profiles
- support `nono` in layouts
- consider sandboxed plain shells via `nono shell`

Until this lands, the UI must keep saying where support begins and ends.

## What I Would Not Build Yet

- Inline TOML profile editor inside Roux
- Full policy builder UI for filesystem/network/secrets
- Session-time live mutation of sandbox permissions
- Per-pane policy editing in layouts

Those all look attractive, but they are larger product bets and depend on backend/state model changes Roux does not have yet.

## Adjacent UX: "Add Folder"

This came up while discussing deeper `nono` integration and it is worth pinning explicitly.

Roux should probably have a quick `Add Folder…` action, but the first version should be a **pane-level** affordance, not a session-level multi-root model.

Recommended first-pass behavior:

- `Open Folder in New Pane…`
- `Split Right in Folder…`
- `Split Down in Folder…`

Why pane-level first:

- Roux already persists pane working directories and can restore live shell cwd later.
- The session model is still single-root (`repoRoot` / `worktreePath`) and many features assume that.
- A true session-level “attach another folder” flow would force decisions about tasks, docs, watches, grouping, and repo identity.

Important distinction:

- `Open a pane in folder X` is a navigation / workspace convenience feature.
- `Grant the sandbox access to folder X` is a security-policy change.

Those should not be the same UI action.

If Roux adds both, the product language should stay explicit:

- `Open Folder in Pane…`
- `Grant Folder to Sandbox…`

This avoids conflating shell cwd with `nono` permissions.

## Backend Implications

The UI above stays honest only if the backend exposes enough state.

Minimum additions:

- Persist sandbox metadata on sessions
- Expose more than just profile names if we want capability summaries
- Add a command for `nono why`

Reasonable API additions:

- `get_nono_status() -> { installed, profiles: NonoProfileSummary[] }`
- `NonoProfileSummary` should include:
  - `id`
  - `name`
  - `description`
  - `workdirAccess`
  - `networkBlocked`
  - `interactive`
  - `secrets`
  - `hooks`
- `nono_why_path(...)`
- `nono_why_host(...)`

If Roux only returns profile names, the UI can show selection but not meaningful summaries.

## Proposed Copy

Launch-time copy:

- `Security`
- `Protect this session with nono's sandbox`
- `This launch path does not support nono yet`
- `Available for built-in Claude sessions`

Session-time copy:

- `Sandboxed`
- `nono profile: claude-code`
- `Network blocked`
- `Project read-only`

Debug copy:

- `Why is this denied?`
- `Check what this session can read, write, or connect to`

## Recommendation

If we implement only one slice next, it should be:

1. persist sandbox metadata on sessions
2. add a session badge
3. reshape `NewSessionDialog` into an explicit `Security` section with honest unsupported-state messaging

If we want one adjacent convenience feature in the same area, it should be pane-level `Open Folder in New Pane…`, persisted as pane cwd, not as a new session-level workspace membership model.

That gives Roux a coherent story immediately, without pretending the deeper integration already exists.
